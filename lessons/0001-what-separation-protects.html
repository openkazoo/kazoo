What a separate ecallmgr node actually protects

Lesson 1 · about 12 minutes · tied to the PR #76 review · revised after a full survey of ecallmgr's AMQP requests

Predict first

Before reading on, write down from memory: what does ecallmgr do on its own, with no kapp answering? List as much as you can.

Two things you said, both right

"Restarting ecallmgr won't end in-progress calls." Correct. Bridged audio lives in FreeSWITCH, a separate OS process. When ecallmgr comes back, ecallmgr_fs_node:init/1 calls sync_channels and rebuilds its channel table from FreeSWITCH (ecallmgr_fs_node.erl:288).

"ecallmgr can't do much without callflow." Mostly correct, and more than the first version of this lesson admitted. Every new call needs a kapp's route response, and most per-call decisions are AMQP requests to a kapp.

Note the direction, though. ruhnet isn't claiming an ecallmgr restart drops calls. The claim is the reverse: restarting or breaking the kapps should leave ecallmgr alone. So ask what state ecallmgr holds that a combined restart would throw away, not whether calls survive.

What ecallmgr owns and does alone

Needs only FreeSWITCH, AMQP and CouchDB, with no kapp in the loop:

  1. The registration table. This is the decisive one. Which phone is registered at which contact lives in an ETS table inside ecallmgr (ecallmgr_registrar.erl:382), filled from reg_success events. When a kapp bridges to a device, ecallmgr resolves the contact from that table (ecallmgr_util.erl:1182 → ecallmgr_registrar.erl:189). On a miss it asks only other ecallmgrs ({'ecallmgr', 'true'}, ecallmgr_registrar.erl:561). It also answers everyone else's reg_query, e.g. Crossbar's registrations API (ecallmgr_registrar.erl:46–60). I found no code that refills the table from FreeSWITCH on boot. The boot-time sync (:451, :400) only flushes FreeSWITCH's XML cache. So when ecallmgr restarts, the table is empty until each phone re-registers.
  2. Cached SIP auth. maybe_query_registrar checks ecallmgr_auth_cache before going to the registrar kapp (ecallmgr_fs_authn.erl:295–299).
  3. FreeSWITCH config. It serves acl.conf and sofia.conf from system config and the DB (ecallmgr_fs_config.erl:162–183).
  4. Channel state and queries. It tracks every channel and answers channel_status_req, query_channels_req and similar queries for the kapps (ecallmgr_fs_channels.erl:56–68).
  5. The FreeSWITCH connections themselves: connecting, pinging, reconnecting.

Putting it together

Take a single-server install where callflow is back up 30 seconds after a restart:

  • ecallmgr on its own node, only the kapps restarted: the registration table survived, so calls to desk phones ring the moment callflow answers routes again.
  • Combined node restarted: callflow is back, but the registration table is empty. Calls to phones fail until each one re-registers, which can take up to its registration expiry: minutes, or up to an hour with long expiries.

That is the concrete version of ruhnet's argument. Two things soften it. With several ecallmgrs, a restarted one can fetch contacts from its peers (:561), so the gap only exists if every ecallmgr restarts at once. And a plain kapp crash doesn't restart the node: kapps start via application:ensure_all_started/1 (kapps_controller.erl:98) and are temporary apps (OTP application docs), and you can restart one in place with restart_app/1 (:139). The node does go down on a full restart (upgrades), or on a VM-wide fault: OOM, the atom table or process limit (system limits), a wedged VM.

Takeaway: on its own, ecallmgr can't put a new call anywhere. What it holds is the registration table: the only record of where every phone is. A separate node keeps that table through kapp restarts and VM-wide faults in the kapps. A combined node loses it, and phones can't be reached until they re-register. Full table in the failure matrix.

Practice

"Combined node" means ecallmgr and the kapps in one BEAM VM.

1. A combined node restarts while two phones are bridged. Their audio?

2. Only the kazoo_apps node restarts. A phone whose creds ecallmgr cached re-registers. Result?

3. A single combined node restarts and callflow is back in 30 s. Someone calls a desk phone with a 3600 s expiry. Result?

4. In a combined node, a kapp's top supervisor dies. Does ecallmgr go down?

5. In a combined node, a kapp leaks memory until the OOM killer fires. What survives?

6. Which claimed benefit of a separate ecallmgr node is not real?

7. Which of these does ecallmgr do with no kapp running?

Back to the PR

PR #76 changes only the fallback default. Kapp-named nodes and nodes with their own kapps list are unaffected, so a production layout with a separate ecallmgr is still fully supported. The question for ruhnet is narrower than "separate or not": which layout should a fresh install get when nobody chose one? If the answer stays "combined", the registration-table gap is the caveat to write down for production operators.
