0. Which piece of ecallmgr state does a combined-node restart throw away?

The claim

rdnn wrote: “There are also statistics that depend on ecallmgr running separately” (PR #76 comment). Lesson 1 asked what a separate node protects. This claim is a different kind: some code works out a node's role by inspecting the node itself, and a combined node gives it an answer it wasn't written for.

The tree uses two ways to tell. Learn to spot both:

TestLooks likeA combined kazoo_apps@host node
By node name"ecallmgr@" ++ _fails: the name says kazoo_apps
By kapp listis_defined(<<"ecallmgr">>, Kapps)passes, but it now also runs every other kapp

A name test drops a combined node entirely. A kapp-list test counts it, but only as an ecallmgr node, so anything that assumes "ecallmgr node ⇒ only ecallmgr" gets mislabelled data.

Case 1: kazoo_stats, a name test

kazoo_stats runs on every node: it's a plain, always-started app in the release (rebar.config:84). Every node publishes VM memory figures. Only nodes named ecallmgr@… add three more:

get_ecallmgr_values(VarList) ->
    case atom_to_list(node()) of
        "ecallmgr@" ++ _ -> get_ecallmgr_values2(VarList);
        _ -> []
    end.

kazoo_stats.erl:204–209

  • reduction: summed over ecallmgr_sup's children (:221). This one is properly scoped to ecallmgr.
  • processes: length(processes()) (:230). That's the whole VM's process count. It reads as ecallmgr's count only on a dedicated node.
  • register-fail: attempts minus successes. But nothing in the tree ever increments register-attempt or register-success. A grep finds only the reader (:212), the SNMP table definition and the MIB. So this is always 0, in any layout.

The consumer is the stats kapp's SNMP agent. Its ecallmgr table expects exactly these fields (stats_handler.erl:162–169; KAZOO-MIB.mib:357).

What a combined node does to it: named kazoo_apps@host, the node sends no ecallmgr row, so the SNMP ecallmgr table is empty. You can't fix that by naming the node ecallmgr@host. A node named after a kapp starts only that kapp, unless KAZOO_APPS or a node-level kapps list overrides it, since name lookup is third in the order (kapps_controller.erl:201–212). Even with an override, processes would then count every kapp's processes.

Case 2: telemetry, a kapp-list test

The telemetry extractor labels each node kamailio, ecallmgr or kapps. Having ecallmgr anywhere in the kapp list wins (kztm_nodes_extractor.erl:68–72). The reducer then counts nodes and versions by that label (waveguide_reducer.erl:147, 158). So a one-node combined install reports 1 ecallmgr node, 0 kapps nodes. Media-server dedupe keys on the same label (:285) and keeps working.

Case 3: jonny5, a kapp-list test that's fine

When a node expires, j5_channels re-syncs its channel table if that node listed ecallmgr (j5_channels.erl:653). It only asks "did ecallmgr go away?", which is true for a combined node too. Use it as the control case: a kapp-list test is only a problem when the code also assumes the node runs nothing else.

rdnn's other point, briefly

start_default_apps/0 starts ?DEFAULT_KAPPS directly and skips the start_which_kapps lookup (kapps_controller.erl:89–91). Run it from sup on a kazoo_apps@ node in a split layout and you get a second ecallmgr. The PR body already flags this function. rdnn's point is that an operator could actually call it.

Takeaway: “statistics depend on ecallmgr running separately” is true, but narrow. One kazoo_stats code path checks the node name. It feeds an SNMP table that only the optional stats kapp serves, and one of its three fields is dead. Telemetry mislabels a combined node rather than losing it. Both are fixable in code: check application:which_applications() instead of the name, and count only ecallmgr's processes. Neither is a reason a fresh install must split.

Practice

1. A combined node named kazoo_apps@host runs ecallmgr. Does it publish reduction?

2. On a dedicated ecallmgr@ node, what does register-fail report?

3. Telemetry sees one combined node. How does it label it?

4. You rename the combined node ecallmgr@host, with no KAZOO_APPS and no node config. What starts?

5. Which ecallmgr check works correctly in a combined node?
